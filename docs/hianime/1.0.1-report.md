## 1. Executive Summary & Context

The HiAnimeTV (`hianime`) connector was developed to evaluate declarative, non-JavaScript extraction on `https://hianimetv.su/`. Testing on the owner's physical iPhone 15 Pro Max running Aroki 2.0.3 (build 16) identified three distinct operational behaviors:
1. **Home and Browse** populate normally.
2. **Opening a show** initially appears to have no episodes; episodes appear after several seconds.
3. **Selecting an episode** on the physical iPhone 15 Pro Max does not start playback.
4. Additionally, Codex flagged a search failure: `CATALOGUE_MISS query=Naruto`.

In strict accordance with architectural boundaries:
- **Zero App Code Modifications**: No code in `app/`, `VireoCore/Sources/`, or test suites was modified.
- **Testing Repository Isolation**: All modifications are strictly committed to `https://github.com/kas021/Testing-Modules-AR`. No changes have been pushed to the signed production index (`AROKI-Connectors`).
- **No Secrets or Ephemeral Signed URLs**: Sensitive temporary playback tokens and signed GoogleVideo links are excluded from this report and repository commits.

## 2. Root Cause Diagnoses

### Issue A: Why Home and Browse Work Normally

**Diagnosis**:
- Home and Browse sections execute the `operations.discovery` block:
  - URL: `https://hianimetv.su/anime/?page={page}`
  - Selector: `div.listupd article.bs div.bsx`
- `hianimetv.su` is a WordPress site running the `animestream` theme. Unlike sites shielded behind Cloudflare Managed Challenges or Turnstile, its archive catalog pages are fully server-side rendered (SSR) HTML.
- Requests sent with standard browser headers (`Accept: text/html`, fixed `User-Agent`) receive HTTP 200 responses with the complete HTML document.
- Aroki's native Swift HTML extractor parses the title (`a.tip[title]`), poster URL (`img.ts-post-image[src]`), and source ID (`a.tip[href]` with `removePrefix`/`removeSuffix`) without requiring any JavaScript evaluation, cookies, or browser session tokens.
- Pagination operates cleanly via standard query parameter substitution (`?page={page}`).

---

### Issue B: Why Episodes Take Several Seconds to Appear on Title Open

**Diagnosis**:
The delay is caused by the combination of two sequential identical network fetches and an unhandled loading state in the SwiftUI interface:

1. **Duplicate Sequential Full-HTML Requests**:
   - In `connector.json`:
     - `operations.details` fetches: `https://hianimetv.su/anime/{titleID}/`
     - `operations.episodes` fetches: `https://hianimetv.su/anime/{titleID}/`
   - In `Aroki/DetailView.swift` (`load()` function, lines 952–956):
     ```swift
     let loadedDetails = try await appState.details(for: canonicalTitle)
     let loadedSeasons = try await appState.seasons(for: canonicalTitle, sharedID: loadedDetails.sharedID)
     details = loadedDetails
     seasons = loadedSeasons
     ```
   - Because `details` and `seasons` are executed sequentially with `await`, the Aroki engine issues two completely distinct network GET requests over HTTPS to `hianimetv.su`.
   - Each request downloads ~204 KB of uncompressed HTML. On mobile network connections, two sequential 204 KB roundtrips require ~1.2 to 2.8 seconds total latency.

2. **Absence of Episode Loading Placeholder in `DetailView`**:
   - When the user opens a title, `DetailView.swift` resets local state:
     ```swift
     details = nil
     seasons = []
     ```
   - In the SwiftUI body rendering (`DetailView.swift`, lines 154–158):
     ```swift
     if !currentEpisodes.isEmpty { primaryButton.arokiReveal(delay: 0.03) }
     if sourceOfferedVariants.count > 1 { audioVariantPicker }
     if seasons.count > 1 { seasonPicker }
     if !currentEpisodes.isEmpty { episodeList.arokiReveal(delay: 0.06) }
     ```
   - `currentEpisodes.isEmpty` remains `true` throughout both sequential network fetches.
   - The view renders only the `hero` banner image and empty space below. There is no progress indicator, skeleton list, or loading state for the episode area.
   - Once the second fetch completes, `seasons = loadedSeasons` is assigned, triggering the `.arokiReveal(delay: 0.06)` animation. To the user, the screen appears empty before the episode list abruptly materializes.

### Issue C: Why Playback Does Not Start on Physical iPhone 15 Pro Max

**Diagnosis**:
While stream resolution and macOS CLI testing (`vireo-tool probe-title`) succeed, playback fails on the physical iPhone 15 Pro Max due to two major technical blockers:

#### 1. iOS AVFoundation `User-Agent` Stripping vs. GoogleVideo `eaua` Signature
- When `hianimetv.su` provides a playable Blogger stream, it extracts a direct GoogleVideo URL (`*.googlevideo.com/videoplayback?...`).
- GoogleVideo URLs generated by Blogger contain an `eaua` (Encrypted / Authenticated User-Agent) query parameter in `sparams`:
  ```text
  &eaua=OfoyTv86HTM&sparams=expire,ei,ip,id,itag,source,requiressl,xpc,susc,svpuc,eaua,mime,vprv,rqh,dur,lmt&sig=...
  ```
- GoogleVideo validates that incoming media segment requests match the exact User-Agent used when Blogger signed the URL.
- In `PlayerScreen.swift`:
  ```swift
  private func assetOptions(for candidate: StreamCandidate) -> [String: Any] {
      guard !candidate.headers.isEmpty else { return [:] }
      let headers = Dictionary(uniqueKeysWithValues: candidate.headers.map { key, value in
          (key.split(separator: "-").map { $0.prefix(1).uppercased() + $0.dropFirst() }.joined(separator: "-"), value)
      })
      return ["AVURLAssetHTTPHeaderFieldsKey": headers]
  }
  ```
- **The Core iOS Failure**: On physical iOS devices, Apple's `AVPlayer` and `AVURLAsset` do NOT reliably forward custom `User-Agent` headers specified in `AVURLAssetHTTPHeaderFieldsKey`. The underlying OS daemon (`mediaserverd` / `AppleCoreMedia`) overrides the request header with Apple's system user agent (e.g., `AppleCoreMedia/1.0.0.21... (iPhone; ...)`).
- When GoogleVideo detects the mismatch between `AppleCoreMedia` and the signed `eaua` token, it rejects the segment request with **HTTP 403 Forbidden**.
- Consequently, `asset.load(.isPlayable)` or `AVPlayerItem.status` transitions to `.failed`, triggering `candidate-startup-failed` in the app.

#### 2. Carrier / IP Address Binding in GoogleVideo `sparams`
- GoogleVideo URLs generated by `hianimetv.su` contain an embedded IP parameter:
  ```text
  &ip=38.154.109.92
  ```
- This IP is the egress address of the `hianimetv.su` backend server that contacted Google/Blogger.
- For certain CDN nodes and regional clusters, GoogleVideo validates the client's IP network against the token. When accessed over cellular networks (LTE/5G), roaming, or iCloud Private Relay, GoogleVideo nodes enforce IP restrictions, returning HTTP 403.

#### 3. Heterogeneous Stream Providers Across Catalog
- HiAnimeTV does NOT use Blogger exclusively. Across the catalog:
  - **Blogger (`source=blogger`)**: Uses JW Player with inline `var fileUrl = "..."`. Natively extractable via `scriptAssignment`.
  - **MegaPlay (`source=hianime`)**: Embedded on titles such as *My Melody to Kuromi*. Uses `megaplay.buzz` with encrypted AES streams. Does NOT have `var fileUrl`.
  - **MegaVid (`source=embed`)**: Uses third-party iframe embed without inline script assignments.
- When an episode defaults to `source=hianime` or `source=embed`, the declarative extraction in `streams` Step 2 fails with `no playable stream candidate`.

### Codex Finding: `CATALOGUE_MISS query=Naruto`

**Diagnosis**:
- **Why It Occurred**: `hianimetv.su` is an unofficial, boutique WordPress streaming site with an index limited to ongoing/recent seasonal releases (e.g., *Oshi no Ko Season 3*, *Jujutsu Kaisen: The Culling Game*, *High School! Kimengumi (2026)*, *'Tis Time for "Torture," Princess*).
- It does **not** carry classic legacy anime such as *Naruto* or *Naruto Shippuden*.
- When a search for `Naruto` is executed (`https://hianimetv.su/?s=Naruto&page=1`), the server returns an empty results container (`div.listupd` with 0 `<article class="bs">` elements).
- The connector parser correctly reports 0 results. The Aroki test runner flags this as `CATALOGUE_MISS query=Naruto`.
- **Conclusion**: This is a genuine content catalog absence on `hianimetv.su`, not an extraction failure, selector regression, or connector defect.

## 6. Proposed Engine Capabilities (Non-JavaScript)

To support sites like HiAnimeTV and similar streaming architectures without compromising Aroki's security model or executing untrusted JavaScript, we recommend the following non-JS engine and application enhancements:

### 1. Document Caching Across Lifecycle Operations
- **Problem**: When a user opens a show, `details` and `episodes` perform two separate HTTP GET requests for the same URL (`/anime/{titleID}/`), causing unnecessary bandwidth usage and a noticeable 2-3 second delay.
- **Solution**: Implement a short-lived (e.g., 5-second) in-memory request deduplication/cache in `ConnectorEngine`. If `episodes` targets the identical URL as `details` for the active title, reuse the parsed `ResponseDocument`. This reduces load time by 50% and eliminates redundant network transfers.

### 2. UI Episode Skeleton / Loading State in `DetailView`
- **Problem**: `DetailView.swift` hides the episode list and primary action button entirely when `seasons.isEmpty`, leading users to believe the title has no episodes.
- **Solution**: Add an explicit episode skeleton or loading indicator in `DetailView.swift`:
  ```swift
  if !currentEpisodes.isEmpty {
      episodeList.arokiReveal(delay: 0.06)
  } else if details != nil && status == nil {
      EpisodeListSkeletonView()
  }
  ```

### 3. Native Local Loopback Proxy for Custom Playback Headers
- **Problem**: On iOS, `AVURLAsset` delegates requests to system daemons (`mediaserverd`), which strip or replace `User-Agent` headers with Apple system strings. This causes immediate HTTP 403 Forbidden errors on providers (such as GoogleVideo `eaua`) that validate the User-Agent against an HMAC signature.
- **Solution**: Provide a native in-app loopback proxy or implement `AVAssetResourceLoaderDelegate`. The player connects to `http://127.0.0.1:<port>/playback?...`, and the local Swift proxy forwards the request with the declared `playbackHeaders` (`User-Agent`, `Referer`) intact. This enables full compatibility with signature-validated streams without requiring any JavaScript.

### 4. Declarative Multi-Server Fallback Extraction
- **Problem**: HiAnimeTV provides multiple server options via Base64-encoded strings or multiple iframes. When the default player is an unsupported provider (e.g., MegaPlay), the connector currently fails.
- **Solution**: Extend the declarative schema to support candidate list evaluation in `streams` (e.g., an array of extraction patterns or fallback selectors) so the engine can evaluate alternative servers if the primary fails.
